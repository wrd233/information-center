# information-center 去重与事件聚合：概念、心智模型与处理逻辑初稿

> 本文不是实现方案，也不是任务清单。它试图回答一个更基础的问题：在 `information-center` 这个项目里，系统为什么需要“去重”和“聚合”，这些概念各自意味着什么，处理链路背后的设计思想是什么，以及在关键环节上应当如何权衡。

---

## 1. 先建立一个整体心智模型

`information-center` 表面上是一个围绕 RSS 信息源建立的内容系统，但如果只把它理解为“抓取 RSS、展示列表、生成简报”，就会低估这个项目真正的复杂度。

这个项目更准确的定位是：**从持续流入的异构信息中，恢复出真实世界的事件结构，并把这些事件变成可以被人阅读、审核和再次利用的情报对象。**

这句话里有三个关键词：**异构信息**、**事件结构**、**情报对象**。

RSS item、网页标题、摘要、发布时间、来源、链接，这些都只是外部世界的碎片。它们不天然等于“事件”。一条内容可能是新闻报道，也可能是周报、观点、教程、市场综述、自动转发、广告，甚至只是同一条内容的重复推送。系统真正要做的，不是把这些碎片机械地存起来，而是逐步判断：哪些只是重复内容，哪些是同一个现实事件的不同报道，哪些只是同一个主题下的相关内容，哪些值得进入最终简报。

因此，这个项目的核心链路可以理解为一条从“内容碎片”到“可信事件”的转换链：

```text
外部信息流
  ↓
原始内容条目 Item
  ↓
内容级去重 Dedupe
  ↓
事件性判断 Eventness
  ↓
事件身份识别 Event Identity
  ↓
候选聚合 Candidate Matching
  ↓
关系裁决 Relation Decision
  ↓
事件簇 Event Cluster
  ↓
事件对象 Event
  ↓
审核、简报、报告 Review / Briefing / Report
```

这条链路里最重要的思想是：**系统不是在“整理标题”，而是在“重建现实事件”。**

---

## 2. 为什么“去重”和“聚合”不能混为一谈

在这个项目里，最容易误解的地方，是把“去重”和“聚合”看成同一种事情。它们确实都在减少信息噪声，但处理的问题完全不同。

**去重解决的是：这是不是同一条原始内容又出现了一次？**

例如同一个 RSS entry 被抓取了两遍，同一个 URL 因为 tracking 参数不同而看起来像两个链接，或者同一个源反复推送同一条内容。这类问题的本质是内容层面的重复。处理它时，系统主要依赖比较确定的依据，比如规范化后的 URL、GUID、来源、标题和发布时间。

**聚合解决的是：这些不同内容是否描述了同一个现实世界事件？**

例如不同媒体都报道了某家公司发布了一个新模型，标题不同、URL 不同、语言不同、发布时间略有差异，但它们指向的是同一件事。这时，系统不能再依赖 URL 或 GUID，而要理解事件背后的主体、对象、动作和时间窗口。

> **补充说明**  
> 内容去重更接近数据库写入层的问题，强调确定性、低成本和可回放。事件聚合更接近语义理解层的问题，强调身份识别、关系判断和证据解释。

如果把这两件事混在一起，会产生严重的认知混乱。用户会分不清某条内容是“重复抓取”，还是“同一事件的另一篇报道”；开发者也会分不清某个模块究竟应该负责消除重复 item，还是负责构建事件簇。最终，前端展示出来的也会是一团模糊的“相似内容”。

所以，在这个项目里，第一条原则就是：**item-level dedupe 与 event-level aggregation 必须分层。**

---

## 3. Item：系统接触现实世界的最小原材料

`Item` 是系统从外部 source 抓到的一条原始内容。它通常来自 RSS feed，对应一篇文章、一个帖子、一条更新、一则简讯，或者某个自动生成的信息条目。

但 item 只是一种原材料。它可以承载事件，也可以不承载事件。它可能是一篇真正的新闻报道，也可能是一篇“本周 AI 行业回顾”。前者可能直接指向一个明确事件，后者则可能包含多个事件、多个主题，甚至只是观点整理。

因此，item 在系统中的地位应该被准确理解为：**它是系统观察到的信息片段，而不是系统最终理解出的事件。**

这一点非常关键。如果系统一看到 item 就急着创建 event，event 表很快会被非事件内容污染。很多 RSS 系统之所以后期难以维护，就是因为一开始没有区分“内容条目”和“事件对象”，导致所有东西都被平铺成同一种数据。

在 `information-center` 里，item 更像是证据材料。它可以被去重，可以被分类，可以被判定为事件候选，也可以被纳入某个事件簇。它的价值不只在于自身，还在于它和其他 item 之间的关系。

---

## 4. Source：不只是抓取入口，也是信号来源

`Source` 表面上是一个 RSS 地址或信息来源，但在这个项目里，它不应该只是一个 URL 列表。

一个 source 长期持续地贡献内容，因此它天然带有稳定性、质量、领域倾向和噪声特征。某些 source 更像新闻源，某些 source 更像社交流，某些 source 经常产生 digest，某些 source 则可能重复推送或生成模板化内容。

这意味着 source 会影响后续判断。同一条信息，如果来自权威官网、主流媒体、二手聚合站、个人社交源，系统对它的解释和权重不应该完全一样。多个独立 source 同时报道同一件事，会增强事件可信度；单一低质量 source 的泛标题，则不应该轻易触发事件物化。

> **设计提示**  
> Source 管理不是“配置管理”的附属功能，而是事件质量控制的一部分。source 的健康度、类型、历史表现和噪声模式，都应该成为事件聚合的上下文。

这也解释了为什么项目需要 source registry、run history、source health 等能力。它们不是简单的运维功能，而是在为后面的事件理解提供基础信号。

---

## 5. 内容去重：把“同一条内容重复出现”折叠起来

内容去重的基本问题很简单：系统又看到了一条 item，它到底是新内容，还是之前已经见过的内容？

这一步应该尽量稳定、确定、低成本。因为它发生在信息写入的入口处，如果判断逻辑过于复杂，就会拖慢整个 pipeline，也会让数据库状态变得不可解释。

内容去重的理想结果不是“丢掉重复内容”，而是**折叠重复内容，同时保留重复出现的事实**。也就是说，当系统再次看到同一条 item 时，不应该简单忽略，而应该记录它又出现了：出现次数增加，最近出现时间更新，必要时保留最新 payload。

这样做的意义在于，重复出现本身也是一种信号。它可能说明 source 重复推送，也可能说明某条内容被重新置顶或更新。但这个信号仍然是 item 层面的，不应该被误读为“这个事件被多来源报道”。

这里有一个重要区分：

| 现象 | 正确理解 |
|---|---|
| 同一 item 的 seen count 很高 | 同一条内容被重复看到 |
| 多个 source 报道同一事件 | 事件覆盖度高 |
| 一个 cluster 中 item 很多 | 事件证据材料多 |

这三者都和“数量”有关，但语义不同。把它们混用，会直接影响前端指标和 briefing 质量。

## 6. 后置去重的重点不是再去重，而是解释

在系统已经具备写入阶段去重之后，后置 dedupe stage 的定位需要重新理解。

如果重复内容已经在入口处被折叠，那么后置阶段未必能看到很多多成员 dedupe group。这不是后置阶段失败，而是说明入口去重已经工作了。此时后置阶段更有价值的任务，不是再次寻找重复，而是解释“去重发生了什么”。

也就是说，后置 dedupe 更像一个观测与解释层。它应该让用户和开发者知道：本轮抓取中有多少新增，有多少重复命中，重复主要来自 URL、GUID、标题日期还是其他规则；哪些 source 重复率高；哪些 item 最近反复出现。

这种解释能力非常重要。因为没有解释，前端只能显示一个模糊的“新增/重复”数字；有了解释，用户才能理解系统为什么没有新增那么多内容，也能判断某些 source 是否质量较差。

> **权衡说明**  
> 后置去重不应该为了“看起来有结果”而人为制造复杂 group。真正重要的是把入口去重的过程、依据和影响讲清楚。对于信息系统来说，可解释性往往比表面上的聚合数量更重要。

## 7. Eventness：系统先要学会拒绝

事件聚合最容易犯的错误，是太急于合并。

事实上，在尝试判断“哪些 item 属于同一事件”之前，系统更应该先判断：**这条 item 是否真的适合作为事件材料。**

这就是 eventness 的意义。

事件性强的内容，通常描述了一个相对明确的现实动作：某个主体发布了某个产品，某家公司完成融资，某个监管机构出台政策，某个模型更新，某个系统发生故障。它有主体，有动作，有对象，有时间窗口。

事件性弱的内容，则可能只是信息合集、行业综述、教程、观点、市场回顾、排行榜、趋势分析或者社交碎片。它们不一定没有价值，但它们不应该被直接当成一个事件。

这里的设计思想是：**事件系统首先要保护 event 表不被污染。**

如果 digest、roundup、tutorial、opinion 这类内容被大量物化为 event，后面所有能力都会变差。事件列表会变吵，聚合候选会变多，review queue 会被塞满，briefing 会越来越像 RSS 摘要，而不是事件简报。

所以，eventness gate 本质上是一个质量闸门。它不是为了追求高召回，而是为了让系统先学会说“不”。

> **关键权衡**  
> 早期阶段，eventness 判断应该偏保守。宁可让一些边界模糊的内容暂时停留在 inbox 或 review 状态，也不要轻易把它们变成正式 event。

## 8. 事件身份：标题不是事件，URL 也不是事件

事件聚合的核心，是识别事件身份。

在现实信息流中，同一事件会被不同来源用不同标题描述。标题可能换词，可能改语序，可能翻译成中文，可能突出不同角度。URL 和 GUID 更不用说，它们只在同一内容或同一 source 内有意义，跨来源时基本不能用来判断事件相同。

所以，事件身份不能建立在标题表面，也不能建立在链接上。它应该建立在更接近现实结构的几个问题上：**谁，对什么，做了什么，发生在什么时间窗口。**

例如：

```text
OpenAI / GPT-5.5 / 发布 / 2026-05-31
```

这比标题更稳定。不同来源可能写成“OpenAI launches GPT-5.5”“OpenAI rolls out new coding model”“OpenAI 发布面向代码智能体的新模型”，但它们背后的事件身份可能是一致的。

当然，这种结构化身份也不是万能的。主体可能有别名，产品可能有多个写法，动作可能表达不同，时间可能有时区差异，标题也可能缺少关键信息。因此，事件身份识别不能被理解成一个一次性精确匹配问题，而应该被理解成一个逐步建立置信度的过程。

这就是 event signature 的位置：它不是最终答案，而是系统把自然语言信息转成可比较结构的中间表达。

---

## 9. Event Signature：事件的结构化指纹

Event signature 可以理解为系统为 item 抽取出的“事件指纹”。它试图把标题和摘要中的自然语言，转换成更稳定的事件身份表达。

它并不是给用户展示的最终文案，而是系统内部用于比较、候选生成和聚合判断的语义支点。

一个好的 signature 应该表达出：这个 item 可能涉及哪个主体，哪个对象，哪个动作，哪个时间窗口，以及它属于什么类型的事件。它也应该表达不确定性，例如主体不明确、动作太泛、内容更像 digest，或者事件性不足。

这里的关键思想是：**signature 是高精度聚合的起点，而不是完整聚合的终点。**

当两条 item 的 signature 高度一致时，它们很可能属于同一事件。这个判断通常精度较高。但现实中很多同一事件因为别名、翻译、标题缺失、抽取误差等原因，不一定能得到完全相同的 signature。因此，如果只依赖 signature exact match，召回会不足。

所以 signature 更适合承担“高可信种子”的角色：它先帮系统找到一批很稳的 same-event 关系，再由候选生成和关系裁决去扩展边界。

> **权衡说明**  
> Signature exact match 的优势是稳，问题是保守。它适合自动合并的第一层安全边界，但不适合成为唯一聚合策略。

---

## 10. 候选生成：先缩小范围，不急着下结论

当系统中有几千条 item 时，不可能让每条 item 和所有其他 item 都进行复杂比较。候选生成的作用，是先从大量内容中找出“可能相关”的对象。

这里要特别注意：**候选不是结论。**

候选生成只是在说：“这两条内容值得进一步比较。” 它不能直接意味着“它们是同一事件”。

例如，同一家公司在同一天可能发布产品、调整价格、回应监管、公布财报。这些 item 可能主体相同，时间接近，主题也相关，但它们不是同一个事件。如果候选阶段直接合并，就会产生严重误合并。

因此，candidate generation 应该被设计成一个召回层，而不是裁决层。它可以尽量找到潜在关系，但最终是否合并，必须交给 relation decision。

> **设计提示**  
> 候选生成可以适度宽一些，关系裁决必须足够严。前者负责“不漏掉值得看的对象”，后者负责“不把不该合的东西合起来”。

这种分工能让系统既保留扩展能力，又不牺牲事件质量。

---

## 11. Relation Decision：从“相似”走向“关系”

很多信息系统会停留在“相似度”的层面：标题相似、embedding 相似、关键词相似、主题相似。但对 `information-center` 来说，这还不够。

因为相似不等于同一事件。

两条内容可能是同一原文的重复，也可能是同一事件的不同报道，也可能是同一事件的新事实补充，也可能只是同一主题下的不同事件。它们在前端、数据库和 briefing 中的处理方式完全不同。

所以，系统真正需要的是 relation decision，也就是判断 item 与 item、item 与 cluster、cluster 与 cluster 之间到底是什么关系。

这一步要回答的不是“像不像”，而是“是什么关系”。

如果是 duplicate，就应该折叠或解释为重复。如果是 same event，就可以进入同一事件簇。如果是 same event with new information，就不只是合并，还要把新增事实提取出来。如果只是 same topic，就不能合并为同一事件，但可以在更高层的主题或报告中关联。如果不确定，就应该进入 review。

这里体现了一个重要设计思想：**系统不能只输出结果，还要输出关系。**

只有关系清楚，前端才能解释，review 才能操作，briefing 才能判断哪些内容有增量价值。

---

## 12. 事件簇：不是一堆相似 item，而是一组可解释证据

Event cluster 很容易被误解成“相似内容分组”。但在这个项目里，事件簇应该被理解为：**围绕同一现实事件形成的一组证据材料及其关系。**

这意味着 cluster 不是简单的 item 列表。它应该有自己的身份，有代表材料，有置信度，有状态，也应该能解释每条 item 为什么属于这里。

一个健康的事件簇应该能回答：这个簇描述的是什么事件？哪些 item 支撑了它？哪些来源参与了报道？哪些 item 只是重复覆盖？哪些 item 带来了新增事实？哪些关系是系统自动判断的，哪些经过人工确认？

如果一个 cluster 不能回答这些问题，它就不是一个可信事件簇，而只是一个不可解释的分组结果。

这也是 legacy cluster 的风险所在。历史上如果存在一些缺少成员关系、缺少证据链、无法回放的 cluster，它们不应该被继续当作可靠事件基础。它们可以作为迁移参考，但不应该成为新系统的核心事实来源。

> **关键判断**  
> 事件簇的价值不在于“把多少 item 放到了一起”，而在于“是否能解释为什么这些 item 应该在一起”。

---

## 13. Event：面向用户消费的事件对象

Event 是从可信 cluster 中物化出来的对象。它是系统希望最终交给用户阅读、审核、进入简报或生成报告的核心单位。

但 event 不应该被简单理解成“cluster 的标题和摘要”。一个真正有价值的 event 应该承载系统对现实事件的理解：这件事是什么、什么时候发生、涉及谁、影响什么、有哪些来源报道、哪些事实是新增的、系统对此有多大把握。

换句话说，event 是从证据集合中提炼出来的“可消费事实对象”。

这里需要保持一个非常重要的约束：**不是所有 cluster 都应该物化为 event。**

只有当事件性足够强、身份足够稳定、关系判断足够可信、负特征不明显、证据链足够完整时，cluster 才适合被物化为 event。否则，它应该停留在候选、主题、review 或非事件状态。

这种设计看起来会让早期 event 数量变少，但它能保护 event 表的可信度。

> **权衡说明**  
> Event 表应该宁缺毋滥。它不是信息垃圾桶，而是系统认为“已经足够像一个真实事件”的对象集合。

---

## 14. Review Queue：不确定性的安全阀

自动化系统最危险的地方，不是“不知道”，而是“不知道自己不知道”。

在事件聚合中，大量判断天然存在边界情况：同一个 actor 的多个动作、同一个产品的不同阶段、digest 中包含多个事件、标题过短、source 质量不稳定、语言表达模糊。这些情况如果被系统强行自动合并，很容易污染事件对象。

Review Queue 的价值就在这里。它不是失败队列，而是安全阀。它让系统在不确定时停下来，把判断权交给用户。

这也是一个成熟信息系统与普通自动摘要工具的重要差别。普通工具倾向于给出一个看似完整的答案；可信系统则应该明确标出哪些是高置信自动结果，哪些需要人工确认。

Review 的目标不是让用户重新读所有 item，而是让用户快速判断系统提出的候选关系是否成立。好的 review 体验应该围绕证据呈现，而不是围绕原文堆叠。用户应该看到系统为什么犹豫、哪里匹配、哪里冲突、如果确认会产生什么事件结果。

---

## 15. Briefing 与 Report：只能消费可信事件

Briefing 和 report 是这个项目最容易让用户感知价值的输出，但它们的质量完全取决于前面的事件处理链路。

如果 briefing 直接消费 raw item，它就是 RSS 摘要。如果 briefing 消费的是弱聚合 event，它就会把前面的误合并、非事件污染和重复内容继续放大。只有当 briefing 消费的是经过 eventness、signature、relation、cluster 和 review 处理后的可信 event，它才会具有真正的情报价值。

这意味着 briefing/report 不应该被看作一个孤立的生成模块。它们是整个 pipeline 的下游消费者。上游事件对象越干净，下游输出越稳定；上游事件对象越混乱，下游再好的 prompt 也只是把噪声重新包装。

> **设计提示**  
> 不要用生成能力掩盖结构问题。简报质量首先来自事件结构质量，其次才来自语言生成质量。

因此，项目后续如果要提升 briefing/report，重点不应首先放在“让文案更好看”，而应放在“输入给 briefing 的 event 是否可信、是否有增量事实、是否已过滤非事件”。

---

## 16. 关键权衡：精度优先还是召回优先

事件系统一定会遇到一个核心权衡：自动聚合应该更激进，还是更保守？

如果更激进，系统看起来会更聪明，能够把更多内容合在一起，前端上 event 数量更少，简报也更集中。但代价是误合并风险上升。一旦不同事件被错误合并，event 对象会被污染，用户很难再信任系统。

如果更保守，系统会产生更多碎片，同一事件可能被拆成多个 event，用户短期内需要多看一些内容。但这些碎片通常可以通过 review、后续合并、规则优化逐步改善。

对于 `information-center` 这样的系统，早期应该选择 **精度优先**。

原因很简单：**漏合并是可修复的，误合并是污染性的。**

漏合并时，用户看到的是多个相近事件，虽然体验不够优雅，但事实没有被扭曲。误合并时，系统把不同事情混成一件事，后续 briefing/report 会基于错误结构继续生成内容，影响会层层放大。

所以，合理的策略应该是：高置信 same-event 自动合并，中置信候选进入 review，低置信或负特征明显的对象不处理。随着评估数据积累，再逐步提高召回。

---

## 17. 关键权衡：规则、语义模型与人工审核如何分工

这个项目不应该走向“全部规则化”，也不应该走向“全部交给 LLM”。

规则适合处理确定性强、成本敏感、可解释性要求高的环节，比如 URL 规范化、GUID 去重、明显 digest 识别、泛标题压制、source 状态判断。

语义模型适合处理自然语言理解、事件身份抽取、跨标题改写、跨语言匹配、关系解释等规则难以覆盖的环节。

人工审核则适合处理边界情况，尤其是系统有候选但证据不足、自动合并风险较高、或涉及重要事件时。

这三者不是互相替代，而是分工协作。

可以把系统理解成三层判断机制：

```text
确定性规则：负责便宜、稳定、明确的判断
语义模型：负责复杂、模糊、跨表达的理解
人工审核：负责高风险、不确定、需要最终确认的判断
```

这种分工背后的思想是：**把每类判断放到最合适的地方，而不是让某一种技术承担所有责任。**

## 18. 关键权衡：前端展示结果，还是展示过程

对于普通 RSS 阅读器来说，前端展示内容列表就够了。但 `information-center` 的前端如果只展示 sources、items、clusters、events，用户仍然会有很重的心智负担。

原因是用户真正关心的不是数据库里有哪些对象，而是系统对信息流做了什么处理。

更符合这个项目的前端心智模型应该是：

```text
这轮抓到了什么？
哪些是新增，哪些是重复？
哪些被判断为事件候选？
哪些被挡在事件之外？
哪些自动聚合成了事件？
哪些需要我审核？
哪些可以进入简报？
```

也就是说，前端不应该只展示静态对象，而应该展示处理过程。

这也是为什么 run detail 非常重要。它不是简单的日志页面，而是用户理解系统行为的窗口。用户需要通过它看到系统的每一步判断，理解为什么本轮新增多或少，为什么某些内容没有进入 event，为什么某些 item 被合并，为什么某些候选进入 review。

> **设计提示**  
> 前端降低心智负担的关键，不是减少页面数量，而是让页面顺着用户的问题展开。

---

## 19. 项目中的处理逻辑可以这样理解

从开发者视角看，这个项目可以被理解为四个连续层次。

第一层是**采集层**。它负责把外部 source 中的内容抓进系统，记录 run，维护 source 状态，保证 item 能稳定进入数据库。这一层关心的是“有没有抓到、抓得是否稳定、哪些是新增”。

第二层是**内容整理层**。它负责规范化 URL、标题、时间和来源，并进行 item-level dedupe。这一层关心的是“同一条内容是否重复出现”。

第三层是**事件理解层**。它负责判断 item 是否具有事件性，抽取事件身份，生成候选关系，做关系裁决，并形成可解释的事件簇。这一层是整个项目最核心也最复杂的部分，因为它开始从内容表面进入现实语义。

第四层是**情报消费层**。它负责把可信事件交给用户审核、阅读、输出简报或报告。这一层关心的是“用户如何消费系统已经理解出的事件”。

这四层对应的不是单纯技术模块，而是四种不同语义：

```text
采集层：我看到了什么
整理层：哪些是重复内容
理解层：哪些属于同一现实事件
消费层：哪些值得呈现给用户
```

如果开发者能保持这个心智模型，很多实现决策会自然变清楚。

---

## 20. 对当前项目阶段的判断

结合现有项目状态，可以认为 `information-center` 已经完成了从“抓取系统”到“操作台系统”的第一阶段。source registry、run history、console、inbox 查询、基础去重等能力，使它已经不只是脚本式 RSS 抓取器。

但它要成为真正的信息情报系统，还需要跨过第二个门槛：**可信事件聚合**。

当前最需要避免的是，在 event object 尚不可信的情况下，继续堆叠前端页面和生成能力。这样会让系统看起来更完整，但核心语义仍然薄弱。更合理的方向，是先把 eventness、event identity、relation decision 和 evidence chain 建稳，再让前端围绕这些处理过程进行展示。

换句话说，接下来的重点不应该是“让系统生成更多东西”，而应该是“让系统每一次合并都有理由，每一个 event 都有证据，每一个不确定判断都能进入 review”。

这才是从 RSS 工具升级为事件情报系统的关键。

---

## 21. 一句话总结

`information-center` 的去重与聚合能力，本质上不是一个标题相似度功能，也不是一个简单的聚类功能，而是一套从原始内容流中恢复现实事件结构的语义处理体系。

它真正要解决的问题不是：

> 如何把列表变短？

而是：

> 如何让系统知道哪些内容是重复的，哪些内容描述的是同一件事，哪些内容只是同一个主题，哪些内容值得进入最终简报，并且能解释自己为什么这么判断？

围绕这个目标，项目的设计应当始终坚持三条主线：

**第一，分层。** 内容去重、事件性判断、事件身份识别、关系裁决、事件物化不能混在一起。

**第二，可解释。** 每一次自动判断都应该留下依据，前端要展示过程，而不是只展示结果。

**第三，保守合并。** 早期宁可漏合并，也不要误合并；不确定的内容进入 review，而不是强行污染事件对象。

当这三条主线成立时，`information-center` 才能真正从“RSS 内容中心”走向“个人/团队信息情报系统”。
