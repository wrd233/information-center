# 面向注意力管理的事件聚合需求文档（初稿）

> 本文档用于补充 `information-center / content_inbox` 中关于去重、事件聚合、信息源价值沉淀的产品与概念需求。它不直接规定代码实现，而是先澄清系统应该服务的阅读目标、处理逻辑和关键权衡。

## 1. 背景：从“去重”走向“注意力管理”

在一个持续抓取 RSS、新闻、社交源、技术博客、产品公告和行业评论的信息系统里，真正困扰用户的往往不是“内容不够多”，而是**同一件事情被太多来源以不同方式反复描述**。

传统意义上的去重，通常解决的是“同一个 URL、同一个 GUID、同一条 RSS item 是否重复入库”。这当然必要，但它只处理了最表层的重复。对用户来说，更消耗注意力的是另一种重复：

**不同来源都在讲同一个事件，但其中很多报道只是浅层复述，没有新增事实、没有独立判断，也没有更深入的解释。**

因此，本项目中的“去重”需要被重新理解。它不应只是一项数据库清洁能力，而应该成为一套面向阅读体验的注意力管理机制：

> 系统需要围绕同一个事件识别多篇报道之间的价值差异，把高价值信息保留下来，把低增量内容折叠起来，把有趣但不适合作为事实主干的观点放到边缘区域，并长期沉淀各个信息源的价值画像。

这意味着，项目的核心目标不是简单地“减少条目数量”，而是帮助用户回答几个更实际的问题：

**这件事到底是什么？哪几篇最值得读？哪些只是重复？哪些提供了新增事实？哪些是观点或评论？哪些信息源在这件事中表现更好？**

---

## 2. 核心心智模型：同一事件下的信息价值分层

过去可以把信息处理链路理解为：

```text
内容碎片 -> 去重 -> 聚合 -> 事件 -> 简报
```

但这个表达仍然偏工程化，也容易让读者误以为系统目标只是“把内容变成事件对象”。更贴近本项目需求的心智模型应该是：

```text
内容进入系统
-> 判断它属于哪件事
-> 判断它对这件事有什么贡献
-> 决定它在阅读界面中的位置
-> 反过来更新信息源价值
```

这个模型更短，也更符合用户真正的阅读行为。

用户不需要看到所有中间处理细节。用户真正需要的是：系统把同一事件下的信息组织成一个可读的层次。

一个理想的事件阅读结构可以被理解为：

```text
事件主卡片
├── 事件摘要：系统综合高价值报道后形成的主干理解
├── 推荐阅读：最值得打开的 1~3 篇原文
├── 关键事实：多来源确认或高可信来源提供的事实
├── 增量信息：不同报道补充出来的新事实、新数据、新表态
├── 深度解释：对背景、原因、影响、技术细节的解释
├── 观点与评论：有价值但不进入事实主干的观察
├── 低增量报道：默认折叠，保留但不占据主阅读空间
└── 来源贡献：本事件中哪些 source 贡献高，哪些只是重复
```

> 补充说明：这里的“事件评论区”不是用户评论区，而是同事件下的外围材料池。它用于收纳社交反应、小观点、低优先级报道、弱信号和不适合进入事实主干的内容。

## 3. 关键概念重新定义

### 3.1 去重：不只是删除重复项

在本项目中，去重至少包含三层含义。

第一层是**原始内容去重**。它处理的是同一条 RSS item 是否重复出现，例如 URL、GUID、标题和发布时间完全一致。这类去重偏确定性，应当尽量在入库阶段完成。

第二层是**同事件聚合**。它处理的是不同来源、不同标题、不同语言的内容是否在描述同一个现实世界事件。这已经不是传统意义上的 duplicate，而是事件身份识别问题。

第三层是**低增量报道折叠**。这是本需求最关注的部分。多篇报道即使不是同一条原始内容，也可能对同一事件没有新增贡献。它们不应反复出现在主阅读流中，而应该被折叠到“更多报道”“低增量报道”或“事件评论区”中。

因此，去重不应被理解为“删掉重复内容”，而应被理解为：

> 识别同类内容之间的贡献差异，并据此重新分配阅读优先级。

### 3.2 事件：组织信息的中心，而不是唯一目的

事件是系统组织信息的中心。它帮助系统把分散 item 放到同一个语境里比较。

但事件本身不是终点。系统真正要服务的是用户对事件的理解。一个事件对象如果只是把多条标题聚在一起，并不能显著降低用户负担；真正有价值的是系统能够告诉用户：

**哪些内容构成事实主干，哪些内容提供新增信息，哪些内容只是重复，哪些内容提供了有趣但边缘的观点。**

### 3.3 报道贡献度：评价单条内容的核心尺度

对同一事件下的报道，系统不应只判断“质量高不高”，而应该判断它对当前事件理解的贡献。

一篇文章本身写得完整，但如果只是复述官方公告，它对当前事件的增量贡献可能不高。另一篇文章很短，但如果补充了关键数字、时间点、当事人表态或独立证据，它的贡献可能很高。

因此，系统评价报道时要从“绝对质量”转向“相对贡献”：

> 这篇报道相对于当前事件已有信息，新增了什么？改变了什么？补充了什么？是否只是重复？

### 3.4 信息源价值：从单一评分走向多维画像

信息源不应该只有一个总分。不同 source 的价值类型不同：有些源快但浅，有些源慢但深，有些源适合发现线索，有些源适合解释背景，有些源只是在某些细分领域表现好。

因此，source profile 应该沉淀的是多维画像，而不是简单的“好源/坏源”。

一个更符合本项目需求的 source 画像，应当关注：

- 它是否经常较早发现事件；
- 它是否经常提供准确、具体、可验证的信息；
- 它是否经常提供别人没有的新增事实；
- 它是否擅长解释背景、原因、影响；
- 它是否经常产生浅层复述和低增量内容；
- 它在哪些主题或领域中表现更好。

> 补充说明：低质量内容不应被粗暴地等同于“这个信息源无价值”。有些 source 的定位本来就是早期线索或社交反应，它们可能不适合作为主阅读来源，但仍然能在发现事件、观察传播、捕捉观点方面提供价值。

## 4. 处理逻辑：从事件归属到阅读位置

围绕上述心智模型，系统处理同事件报道时，可以抽象为四个判断。

### 4.1 它属于哪件事

系统首先需要判断一条内容描述的是不是某个已有事件，或者是否应该形成一个新的事件候选。

这里的核心不是标题是否相同，而是事件身份是否一致。事件身份通常来自主体、对象、动作和时间窗口。例如，同一个公司发布同一个产品、同一个监管机构做出同一个处罚、同一个模型完成同一次版本更新，哪怕标题表达不同，也应被视为同一事件的候选报道。

这一步需要保持谨慎，因为误把不同事件合到一起，会污染后续所有判断。

### 4.2 它对这件事有什么贡献

当内容被归入某个事件后，系统应该继续判断它的贡献角色。

它可能是主干事实来源，也可能是增量事实来源；它可能提供解释和背景，也可能只是把已有信息重新表述了一遍；它可能是观点性内容，也可能是明显低质噪声。

这里的关键是上下文比较。系统不能孤立地评价一篇报道，而要把它放在当前事件已经拥有的信息集合中判断：

**它补充了什么？重复了什么？有没有独立证据？有没有独特视角？有没有让事件理解更深？**

### 4.3 它应该放在阅读界面的哪里

报道贡献度判断之后，系统不一定要删除内容，而是决定展示位置。

高价值内容应该进入事件主卡片、推荐阅读、关键事实或增量信息区域；中等价值内容可以进入补充材料或观点区域；低增量内容应该默认折叠；明显噪声可以隐藏但保留可追溯路径。

这一步体现的是产品思想：

> 系统不是替用户做一次性删除，而是替用户管理注意力。

### 4.4 它如何反过来影响 source 画像

每一条报道在事件中的表现，都可以反过来更新信息源画像。

如果某个 source 多次提供高价值增量事实，它的增量价值应该上升。如果某个 source 经常只是改写别人的内容，它的阅读优先级应该下降。如果某个 source 经常很早发现事件但解释很浅，它可以被标记为“发现价值高、解释价值低”。

最终，source 画像会反过来影响未来抓取、排序、聚合和简报生成。

## 5. 报道贡献度的判断维度

报道贡献度不建议只打一个简单分数。更合理的方式是判断它在事件中的角色，然后再形成阅读优先级。

### 5.1 主干事实价值

一篇报道如果能够清楚说明事件的基本事实，例如谁做了什么、何时发生、涉及什么对象、官方如何表述、影响范围是什么，就具有主干事实价值。

这类内容适合作为事件摘要的主要依据，也适合作为推荐阅读。

### 5.2 增量事实价值

一篇报道如果提供了已有内容没有覆盖的新事实，例如新的数字、时间线、引用、产品细节、影响范围、技术指标、监管进展，就具有增量事实价值。

它不一定是最长、最完整的报道，但它可能对事件理解非常关键。

### 5.3 解释价值

一篇报道如果能讲清楚背景、原因、行业影响、技术含义、利益相关方变化，就具有解释价值。

解释价值不一定等同于事实新增，但它能帮助用户理解“为什么这件事重要”。

### 5.4 观点价值

一篇内容如果提供了独特观察、判断、评论或反应，但不适合作为事实主干，就具有观点价值。

这类内容适合放入“事件评论区”或“观点与反应”区域，而不是和事实报道混在一起。

### 5.5 低增量重复

一篇报道如果只是改写标题、复述已有事实、没有独立来源、没有新增信息、没有解释深度，就属于低增量重复。

这类内容不应删除，但应降低阅读优先级，默认折叠展示。

### 5.6 噪声内容

如果内容明显标题党、营销化、信息密度极低、事实不清、泛泛而谈，或与事件关系弱，则应作为噪声处理。

噪声可以隐藏，但不建议在早期直接物理删除，因为系统判断仍可能出错。

---

## 6. 阅读优先级的基本策略

系统应该把事件下的内容分成不同阅读层级。

第一层是**必须读**。这包括主干事实来源、官方公告、权威报道、高增量事实来源。

第二层是**值得读**。这包括深度解释、有独特观点、提供背景和影响分析的内容。

第三层是**可选读**。这包括观点、社交反应、小补充、领域内观察。

第四层是**默认折叠**。这包括浅层复述、低增量转载、标题改写型内容。

第五层是**隐藏但可追溯**。这包括明显噪声、低质量内容、与事件关系较弱的内容。

> 补充说明：这里的“折叠”不是丢弃，而是降低它在用户注意力中的位置。用户需要时仍然可以展开查看，系统也可以继续利用这些材料观察传播范围和 source 行为。

---

## 7. 信息源画像的沉淀逻辑

信息源价值应该由它在大量事件中的表现逐渐积累，而不是由单条内容一次性决定。

一个 source 每次参与事件时，都可以留下贡献记录：它是否较早发现事件，是否提供主干事实，是否提供增量信息，是否提供深度解释，是否只是重复，是否产生噪声。

长期看，系统可以形成几类 source 画像。

一种是**发现型 source**。它经常较早捕捉到事件，但报道可能短、浅、碎。这类 source 适合用于早期提醒，不一定适合作为推荐阅读。

一种是**事实型 source**。它提供的信息具体、可靠、可验证，适合作为事件主干依据。

一种是**解释型 source**。它不一定最快，但能提供背景、分析和影响判断，适合作为深度阅读来源。

一种是**观点型 source**。它事实贡献不一定高，但经常提供有趣评论或行业反应，适合进入事件评论区。

一种是**重复型 source**。它经常复述已有信息，新增价值低，应降低阅读优先级。

一种是**噪声型 source**。它经常产生低质量、营销化、标题党或弱相关内容，应在未来抓取和展示中被降权。

这种 source profile 的价值在于，它可以让系统越来越懂用户的信息偏好，也能让后续简报更稳定地优先选择高价值来源。

## 8. 关键权衡

### 8.1 折叠，而不是过早删除

低增量内容不应该直接删除。早期系统判断不可能完全准确，如果误删，后续很难恢复。

更稳妥的策略是：**主阅读流降权，后台仍保留，必要时可展开和回溯。**

这也是本项目和普通去重系统的差异。普通去重关心“留一条还是多条”；本项目更关心“哪条应该占据注意力”。

### 8.2 贡献度判断要防止偏爱长文

大模型在判断内容深度时，可能天然偏好长文、结构化表达和看起来专业的语言。但短内容也可能包含关键事实。

因此，系统不应简单把“长、完整、会分析”视为高价值，而应重点判断：

**它是否提供了新事实、独立证据、关键引用、明确数据，或者改变了当前事件理解。**

### 8.3 信息源扣分不能太粗暴

某个 source 提供了一次低增量报道，不代表这个 source 整体低价值。它可能适合发现事件，不适合解释事件；也可能在某些主题上强，在另一些主题上弱。

因此，source 评分应当按角色和领域累积，而不是简单地加分或扣分。

### 8.4 同事件判断要保守，贡献度判断可以更积极

判断两条内容是否属于同一事件时，要保守。误合并会污染事件。

但在同一事件内部判断报道贡献度时，可以更积极。即使贡献度判断有偏差，也只是影响排序和折叠，风险低于错误合并。

这意味着系统可以把大模型更多用于“同事件内部的价值比较”，而不是完全依赖大模型做强制聚合。

## 9. 对前端体验的启发

前端不应把用户暴露在过多底层概念中，例如 dedupe key、signature、candidate、relation、cluster 等。这些概念可以存在于后端和调试页面，但用户日常使用时应该看到的是更自然的事件阅读体验。

事件页面可以围绕几个问题组织：

**这件事是什么？为什么重要？哪些报道最值得读？哪些内容提供了新增事实？有哪些观点可以参考？哪些报道已被折叠？哪些信息源在这件事中表现最好？**

Run Detail 和 Debug 页面可以展示更细的处理证据，但主阅读页面应以“事件下的信息价值分层”为核心。

---

## 10. 一句话需求定义

本项目在去重和事件聚合方向上的目标，可以概括为：

> 系统不是简单替用户收集信息，而是替用户管理注意力：围绕同一个事件保留事实主干和高价值增量，把浅层重复报道折叠起来，把小观点和外围声音放入事件评论区，同时长期学习哪些信息源更值得读。

这个目标比“RSS 去重”更准确，也比“事件聚合”更贴近实际使用体验。
